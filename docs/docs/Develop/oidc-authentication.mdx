# OIDC Authentication (SSO)

Langflow supports OpenID Connect (OIDC) authentication for enterprise Single Sign-On (SSO) deployments. This allows you to integrate with identity providers like Azure AD (Microsoft Entra ID), Google Workspace, Okta, Auth0, Keycloak, and any other OIDC-compliant provider.

## Benefits

- **Enterprise SSO**: Use your organization's existing identity provider
- **Centralized access control**: Manage users in one place
- **Enhanced security**: Leverage MFA and conditional access policies from your IdP
- **Automatic provisioning**: Users are created automatically on first login
- **No password management**: Users authenticate through your identity provider

## Quick Start

To enable OIDC authentication, configure these environment variables:

```bash
LANGFLOW_OIDC_ENABLED=true
LANGFLOW_OIDC_PROVIDER_NAME="Your Provider"
LANGFLOW_OIDC_CLIENT_ID=your-client-id
LANGFLOW_OIDC_CLIENT_SECRET=your-client-secret
LANGFLOW_OIDC_ISSUER_URL=https://your-provider-issuer-url
LANGFLOW_OIDC_REDIRECT_URI=https://your-langflow-domain.com/api/v1/auth/oidc/callback
```

## Configuration Reference

### Required Settings

| Environment Variable | Description | Example |
|---------------------|-------------|---------|
| `LANGFLOW_OIDC_ENABLED` | Enable OIDC authentication | `true` |
| `LANGFLOW_OIDC_CLIENT_ID` | OAuth2 Client ID from your provider | `abc123...` |
| `LANGFLOW_OIDC_CLIENT_SECRET` | OAuth2 Client Secret | `secret123...` |
| `LANGFLOW_OIDC_ISSUER_URL` | OIDC Issuer URL (used for discovery) | `https://accounts.google.com` |
| `LANGFLOW_OIDC_REDIRECT_URI` | Callback URL for your Langflow instance | `https://langflow.example.com/api/v1/auth/oidc/callback` |

### Optional Settings

| Environment Variable | Description | Default |
|---------------------|-------------|---------|
| `LANGFLOW_OIDC_PROVIDER_NAME` | Display name shown on login button | `"OIDC"` |
| `LANGFLOW_OIDC_SCOPES` | OAuth2 scopes to request | `"openid profile email"` |
| `LANGFLOW_OIDC_AUTO_PROVISION_USERS` | Automatically create users on first login | `true` |
| `LANGFLOW_OIDC_REQUIRE_EMAIL_VERIFIED` | Require email verification from IdP | `true` |
| `LANGFLOW_OIDC_DISABLE_LOCAL_AUTH` | Disable username/password authentication | `false` |
| `LANGFLOW_OIDC_ALLOW_SUPERUSER_LOCAL_AUTH` | Allow superuser emergency access via local auth | `true` |

### Advanced Settings (Override Discovery)

These are optional and only needed if your provider doesn't support OIDC discovery:

| Environment Variable | Description |
|---------------------|-------------|
| `LANGFLOW_OIDC_AUTHORIZATION_ENDPOINT` | Override authorization endpoint URL |
| `LANGFLOW_OIDC_TOKEN_ENDPOINT` | Override token endpoint URL |
| `LANGFLOW_OIDC_USERINFO_ENDPOINT` | Override userinfo endpoint URL |
| `LANGFLOW_OIDC_JWKS_URI` | Override JWKS URI |

## Provider Setup Guides

### Azure AD (Microsoft Entra ID)

#### 1. Register Application in Azure Portal

1. Go to [Azure Portal](https://portal.azure.com/) → **Azure Active Directory** → **App registrations**
2. Click **New registration**
3. Configure:
   - **Name**: `Langflow OIDC`
   - **Supported account types**: Choose based on your needs
   - **Redirect URI**:
     - Type: `Web`
     - URI: `https://your-langflow-domain.com/api/v1/auth/oidc/callback`
4. Click **Register**

#### 2. Configure Authentication

1. In your app registration, go to **Authentication**
2. Under **Implicit grant and hybrid flows**:
   - ✅ Check **ID tokens (used for implicit and hybrid flows)**
3. Click **Save**

#### 3. Create Client Secret

1. Go to **Certificates & secrets** → **Client secrets**
2. Click **New client secret**
3. Add description: `Langflow OIDC Secret`
4. Choose expiration period
5. Click **Add**
6. **Copy the secret value immediately** (you won't be able to see it again)

#### 4. Configure API Permissions

1. Go to **API permissions**
2. Ensure these Microsoft Graph permissions are granted:
   - `openid`
   - `profile`
   - `email`
3. Click **Grant admin consent** (if required)

#### 5. Get Configuration Values

- **Client ID**: Found on the **Overview** page (Application/Client ID)
- **Tenant ID**: Found on the **Overview** page (Directory/Tenant ID)
- **Client Secret**: The value you copied in step 3

#### 6. Configure Langflow

Most OIDC providers expose a discovery document at:

## Security Options

### Enforce SSO-Only Authentication

To disable local username/password authentication and require OIDC:

```bash
LANGFLOW_OIDC_DISABLE_LOCAL_AUTH=true
```

This ensures all users must authenticate through your identity provider.

### Emergency Superuser Access

Even with SSO-only mode, you can allow the superuser to login locally for emergency access:

```bash
LANGFLOW_OIDC_DISABLE_LOCAL_AUTH=true
LANGFLOW_OIDC_ALLOW_SUPERUSER_LOCAL_AUTH=true  # Default
```

This provides a safety net if your identity provider becomes unavailable.

### Email Verification

Require users to have verified emails:

```bash
LANGFLOW_OIDC_REQUIRE_EMAIL_VERIFIED=true  # Default
```

Langflow will check the `email_verified` claim from your identity provider.

### Auto-Provisioning

Control whether users are automatically created on first login:

```bash
LANGFLOW_OIDC_AUTO_PROVISION_USERS=true  # Default
```

If disabled, users must be created manually in Langflow before they can log in via OIDC.

## User Management

### How Users Are Created

When a user logs in via OIDC for the first time:

1. Langflow validates the ID token from your identity provider
2. Checks if an OIDC identity with the same `subject` (sub claim) exists
3. If not, checks if a user with the same email exists
4. If no existing user:
   - Creates a new user (if auto-provisioning is enabled)
   - Links the OIDC identity to the user
   - Sets the user as active

### Email Matching

If a user already exists in Langflow with the same email address, the OIDC identity will be linked to that existing user account.

### Multiple Identity Providers

Users can link multiple OIDC identities (e.g., both Azure AD and Google) to the same Langflow account if they share the same email address.

## Known Limitations

### Multi-Instance Deployments

:::warning Important for Production
The current OIDC implementation uses **in-memory state storage** which has the following limitations:

1. **Does not work with multiple Langflow instances** (load balancers, Kubernetes replicas with >1 pod)
2. **State is lost on server restart** (users mid-authentication will need to retry)
3. **No automatic cleanup** of expired state tokens

**Impact**: In a load-balanced environment, if a user's callback request is routed to a different instance than where they initiated login, authentication will fail with "Invalid state parameter".
:::

#### Workaround for Multi-Instance Deployments

Until state storage is migrated to Redis/database, use one of these approaches:

**Option 1: Session Affinity (Sticky Sessions)**
Configure your load balancer to use sticky sessions based on cookies:

```yaml
# Example for Kubernetes with NGINX Ingress
metadata:
  annotations:
    nginx.ingress.kubernetes.io/affinity: "cookie"
    nginx.ingress.kubernetes.io/session-cookie-name: "langflow-oidc"
    nginx.ingress.kubernetes.io/session-cookie-max-age: "300"
```

**Option 2: Single Instance**
Run only one Langflow instance when using OIDC authentication.

**Option 3: Implement Redis Storage (Contribution Welcome)**
The codebase is structured to easily swap in Redis storage. See `/home/user/langflow/src/backend/base/langflow/api/v1/oidc.py` line 29-38.

## Troubleshooting

### "Invalid state parameter" Error

**Cause**: The state parameter used for CSRF protection has expired or is invalid.

**Solution**:
- Try logging in again
- For production deployments with multiple instances, use Redis or a database for state storage instead of in-memory storage

### "Email verification is required" Error

**Cause**: Your identity provider indicates the user's email is not verified.

**Solution**:
- Ask the user to verify their email with the identity provider
- Or disable the requirement: `LANGFLOW_OIDC_REQUIRE_EMAIL_VERIFIED=false`

### "User not found and auto-provisioning is disabled" Error

**Cause**: The user doesn't exist in Langflow and auto-provisioning is disabled.

**Solution**:
- Enable auto-provisioning: `LANGFLOW_OIDC_AUTO_PROVISION_USERS=true`
- Or manually create the user in Langflow with the same email address

### "Failed to fetch OIDC configuration" Error

**Cause**: Langflow cannot reach the identity provider's discovery endpoint.

**Solution**:
- Verify `LANGFLOW_OIDC_ISSUER_URL` is correct
- Check network connectivity from Langflow to the identity provider
- Manually configure endpoints using `LANGFLOW_OIDC_AUTHORIZATION_ENDPOINT`, etc.

### "Invalid redirect URI" Error

**Cause**: The redirect URI in your identity provider doesn't match the one Langflow is using.

**Solution**:
- Ensure `LANGFLOW_OIDC_REDIRECT_URI` exactly matches what's configured in your identity provider
- Check for http vs https, trailing slashes, and port numbers

### Login Button Not Appearing

**Cause**: OIDC is not properly enabled or frontend can't fetch configuration.

**Solution**:
- Verify `LANGFLOW_OIDC_ENABLED=true`
- Check browser console for errors
- Verify the `/api/v1/auth/oidc/config` endpoint is accessible

### HTTPS Required

Most identity providers require HTTPS for redirect URIs in production. For local testing:
- Use `ngrok` or similar tunnel service
- Or configure your identity provider to allow http://localhost

## Security Best Practices

1. **Always use HTTPS** in production
2. **Rotate client secrets** regularly
3. **Restrict redirect URIs** to your actual Langflow domains
4. **Enable email verification** requirements
5. **Use short-lived access tokens** (configured in your IdP)
6. **Enable MFA** in your identity provider
7. **Monitor login logs** in both Langflow and your IdP
8. **Store secrets securely** (use secret management tools, not plain text)

:::caution Important
Never commit OIDC client secrets to version control. Use environment variables or secret management solutions.
:::
